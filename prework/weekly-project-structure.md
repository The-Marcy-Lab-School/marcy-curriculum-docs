## Week 1: Choose a clear idea

**Driving question**: What am I trying to make, and what is the smallest version that could work?

**Goal**: By the end of Week 1, you should have a clear idea and a small plan. Your project idea can change later, but you need a starting point.

### If you need more structure

Start with one of these project frames:

- **Collector game:** A player moves around collecting objects. A score changes.
- **Quiz game:** A player answers questions. A score changes.
- **Virtual pet:** A pet’s mood, hunger, or energy changes based on user choices.
- **Interactive story:** A character makes choices that change the story.

Then answer these questions:

| Question                                          | Your answer |
| ------------------------------------------------- | ----------- |
| What is the user trying to do?                    |             |
| What changes while the project runs?              |             |
| What are two variables I might use?               |             |
| What is one event that should happen?             |             |
| What is the smallest version I could build first? |             |

Example: “I am building a collector game where the player catches stars. The smallest version is one sprite that moves, one star to collect, and a score that increases.”

### Stretch goal: Learn from game design

If you already have a clear starting idea and want to go deeper, your job is not just to make a game — it is to start learning how game designers think.

**Stretch driving question:** What can I learn from existing games that might help me design my own?

Try this:

- Play or inspect 2–3 Scratch games.
- Notice what makes each game clear, fun, confusing, challenging, or satisfying.
- Write down one design move you might try in your own project.

Your stretch goal this week is to write a short design note: **What did I notice from other games, and what idea do I want to try in mine?**

### Concept Check submission

Submit a short written description of:

1. What you plan to build.
2. The smallest version that could work.
3. Two variables you might use.
4. One place you may need help.

## Week 2: Build and test one working piece

**Driving question**: What is one working piece I can build, test, and improve?

**Goal**: By the end of Week 2, you should have a working version of at least one important part of your project. It does not need to be finished.

### If you are struggling to get the basics working

Focus only on one small loop or interaction first. Do not try to build the whole project yet.

Try this sequence:

- [ ]  Make one sprite appear.
- [ ]  Make something happen when the green flag is clicked.
- [ ]  Add a `forever` or `repeat` loop.
- [ ]  Make one variable show on the screen.
- [ ]  Make the variable change.
- [ ]  Add one `if` statement.
- [ ]  Test after each change.

Use this debugging frame when something does not work:

| Debugging question                               | Your notes |
| ------------------------------------------------ | ---------- |
| What did I expect to happen?                     |            |
| What actually happened?                          |            |
| What block or sprite might be causing the issue? |            |
| What is one small test I can try?                |            |
| What question should I ask for help?             |            |

If you can make one loop work and explain what it does, that is real progress.

### Stretch goal: Test a design idea

If your basic project is working, use this week to test one game design idea. Do not add features just to add features. Choose one thing you want to learn about how players experience your project.

**Stretch driving question:** What design choice can I test to learn whether my game is clearer, more fun, or more interesting?

Try this:

- Choose one design idea from a game you played or inspected.
- Add the smallest version of that idea to your project.
- Let someone else try it, or test it yourself as if you were a new player.
- Notice what changed.

Your stretch goal this week is to write: **I changed [something] because I wanted to learn whether [question]. What I noticed was [observation].**

### Progress Check submission

Submit a screenshot or short screen recording showing:

1. One part that works.
2. One thing you are still trying to figure out.
3. One change you made after testing.

## Week 3: Finish, simplify, and prepare to explain

**Driving question**: What version can I finish, explain, and be proud of?

**Goal**: By the end of Week 3, your goal is to finish a version that meets the requirements and that you can explain clearly. This is not the week to make the project much bigger. This is the week to decide what matters most, simplify if needed, and prepare to explain your thinking.

### If you need to simplify

Use this minimum viable project check:

- [ ]  I have at least two variables that change while the project runs.
- [ ]  I have a main loop.
- [ ]  I have at least one conditional.
- [ ]  I have one nested conditional, even if it is simple.
- [ ]  I use broadcast and `when I receive`.
- [ ]  I can explain what each required part does.

If your idea feels too big, reduce it:

| Instead of...            | Try...                                  |
| ------------------------ | --------------------------------------- |
| Many levels              | One level that works                    |
| Many characters          | Two sprites that interact               |
| A complex scoring system | One score variable that changes clearly |
| A long story             | One scene with a meaningful choice      |
| Many features            | One feature you can explain well        |

A smaller project that works and that you understand is better than a larger project that you cannot explain yet.

### Stretch goal: Explain your game design learning

If your project meets the requirements, use the final week to make one intentional improvement and explain why it matters.

**Stretch driving question:** What have I learned about game design, and how did that learning change my final project?

Try this:

- Choose one improvement that makes the experience clearer, more intentional, or more interesting.
- Make the smallest version of that improvement.
- Test the project again.
- Be ready to explain the design choice, not just the code.

Your stretch goal is to prepare this explanation: **At first, my project [worked this way]. After learning more about game design, I changed [one design choice] because [reason].**

### Final check

Before submitting, answer:

| Reflection question                                 | Your answer |
| --------------------------------------------------- | ----------- |
| What did I build?                                   |             |
| What is the smallest version that worked?           |             |
| What did I change or improve?                       |             |
| What bug or challenge did I run into?               |             |
| How did I try to solve it?                          |             |
| What part of my project am I most ready to explain? |             |
